"""
Data validation — fail loudly on bad data *before* it reaches training.

Plain pandas on purpose (no pandera / Great Expectations): the dataset has one
table and ~20 columns, so a dependency would add more weight than it removes.
`validate_raw` is called by eda.load_data(), so every path that loads the CSV
(EDA, training, tests) gets checked.
"""
import json
import os
import pandas as pd

EXPECTED_COLUMNS = [
    "customerID", "gender", "SeniorCitizen", "Partner", "Dependents", "tenure",
    "PhoneService", "MultipleLines", "InternetService", "OnlineSecurity",
    "OnlineBackup", "DeviceProtection", "TechSupport", "StreamingTV",
    "StreamingMovies", "Contract", "PaperlessBilling", "PaymentMethod",
    "MonthlyCharges", "TotalCharges", "Churn",
]
🎯

Why is it used in this project?

Establishes a strict contract for the incoming raw dataset. By explicitly defining the exact 21 expected columns as an immutable list at the top of the file, any schema drift, accidental column renaming, or dropped columns in the CSV are immediately caught before any downstream preprocessing or training begins.
🔀

Was there any other way? (Alternative Approaches)

🔀 Alternative: Great Expectations
A heavy enterprise data testing suite. It requires JSON configuration suites, CLI init steps, checkpoint runners, and heavy external libraries.
🔀 Alternative: Pandera
A statistical data validation library for Pandas DataFrames with type schemas and decorators. Requires extra pip dependencies and learning a specialized DSL.
🔀 Alternative: Pydantic (applied row-by-row)
Validating individual rows via Pydantic models in a loop. Highly expressive but slow for thousands of rows compared to vectorized Pandas checks.
⚖️

Why we used this specific approach over alternatives

Zero Dependency & High Execution Speed: Plain Pandas adds 0 extra dependencies to the project. The dataset is a single table of ~7,000 rows and 21 columns; pulling in Great Expectations or Pandera adds installation fragility and docker image bloat without solving any problem that 10 lines of native Pandas cannot solve faster.
🧠

Memory Hook & Pattern to Remember (Cheat Sheet / Viva Tip)

Rule of Contract: Always freeze column names as an explicit list (EXPECTED_COLUMNS). Check schema at the gateway before writing any transformation code.

class DataValidationError(ValueError):
    """Raised with *every* problem found, not just the first."""
🎯

Why is it used in this project?

Provides a distinct, dedicated exception class for all validation failures. By inheriting from built-in ValueError, standard exception handlers can still catch it as a value error, while caller code or test runners can specifically catch DataValidationError.
🔀

Was there any other way? (Alternative Approaches)

🔀 Alternative: Generic Exception / ValueError
Raising plain ValueError or Exception directly. Makes it hard for unit tests to distinguish data schema violations from general runtime programming bugs.
🔀 Alternative: AssertionError (assert statements)
Using assert condition, 'error'. Dangerous because Python optimizations (python -O) strip out all assert statements entirely in production environments!
⚖️

Why we used this specific approach over alternatives

Precise Exception Hierarchy: It allows callers and test suites to selectively catch validation-specific failures without accidentally masking unexpected internal bugs, while preserving standard ValueError semantics.
🧠

Memory Hook & Pattern to Remember (Cheat Sheet / Viva Tip)

Subclass Built-ins: class DataValidationError(ValueError): pass gives you a specialized error type while remaining compatible with standard error-handling conventions.

def validate_raw(df: pd.DataFrame) -> None:
    errors = []

    missing = [c for c in EXPECTED_COLUMNS if c not in df.columns]
    extra = [c for c in df.columns if c not in EXPECTED_COLUMNS]
    if missing:
        errors.append(f"missing columns: {missing}")
    if extra:
        errors.append(f"unexpected columns: {extra}")
    if missing:  # nothing further can be checked reliably
        raise DataValidationError("; ".join(errors))
🎯

Why is it used in this project?

Checks for missing columns and unexpected extra columns simultaneously. Collects all column-level discrepancies into an errors list so the developer sees every problem at once rather than fixing one missing column, rerunning, and finding another.
🔀

Was there any other way? (Alternative Approaches)

🔀 Alternative: Failing on the first missing column
Using if c not in df: raise Error inside a loop. Forces developers into a frustrating 'whack-a-mole' debugging cycle where one error is reported per run.
🔀 Alternative: Silently dropping extra columns
Writing df = df[EXPECTED_COLUMNS]. Masks data drift or upstream breaking changes (e.g., if a column was accidentally renamed to something new).
⚖️

Why we used this specific approach over alternatives

Fail Complete & Fail Loud: Aggregating errors into a list before raising means all schema errors are surfaced in a single run. If columns are missing, it halts immediately because downstream value checks would raise unhandled KeyError exceptions.
🧠

Memory Hook & Pattern to Remember (Cheat Sheet / Viva Tip)

Accumulate Then Raise: Collect errors in a list (errors = []) and join them into a single comprehensive exception. Break early only if prerequisite fields are absent.

def build_dataset_summary(df: pd.DataFrame, file: str = "data/telco_churn.csv") -> dict:
    numeric = {"SeniorCitizen", "tenure", "MonthlyCharges", "TotalCharges"}
    columns = []
    for c in df.columns:
        s = df[c]
        blank = int((s.astype(str).str.strip() == "").sum())
        columns.append({
            "name": c,
            "kind": "id" if c == "customerID" else "number" if c in numeric else "category",
            "unique": int(s.nunique()),
            "missing": int(s.isna().sum()) + blank,
            "examples": [str(v) for v in s.dropna().unique()[:3]],
        })
    churned = int((df["Churn"] == "Yes").sum())
    return {
        "source": "IBM Telco Customer Churn (public sample dataset)",
        "file": file,
        "rows": int(len(df)),
        "column_count": int(df.shape[1]),
        "churned": churned,
        "retained": int(len(df)) - churned,
        "churn_rate": round(churned / len(df), 4),
        "columns": columns,
        "sample": json.loads(df.head(8).to_json(orient="records")),
    }

def write_dataset_summary(df: pd.DataFrame, out_dir: str) -> str:
    path = os.path.join(out_dir, "dataset_summary.json")
    with open(path, "w") as f:
        json.dump(build_dataset_summary(df), f)
    return path

def load_data(path: str = DATA_PATH) -> pd.DataFrame:
    """Load the raw CSV and apply the minimal cleaning every downstream step needs."""
    df = pd.read_csv(path)
    validate_raw(df)  # raises DataValidationError listing every problem found
    # TotalCharges is stored as a string and has 11 blank values (all tenure == 0,
    # i.e. brand-new customers who haven't been billed yet) — coerce to numeric and
    # impute with the median rather than dropping the rows.
    df["TotalCharges"] = pd.to_numeric(df["TotalCharges"], errors="coerce")
    df["TotalCharges"] = df["TotalCharges"].fillna(df["TotalCharges"].median())
    return df
🎯

Why is it used in this project?

Acts as the single point of truth for data ingestion across the entire repository. Calls validate_raw(df) to verify schema, converts TotalCharges to numeric, and imputes the 11 blank new-signup values with the median. Both eda.py and train_model.py use this identical loader.
🔀

Was there any other way? (Alternative Approaches)

🔀 Alternative: Dropping the 11 blank rows (df.dropna)
Discards real customers who have tenure=0. Leads to loss of brand-new customer representation.
🔀 Alternative: Imputing TotalCharges with 0.0
Logical since tenure=0, but can introduce artificial spikes at 0 in linear models unless specially normalized.
🔀 Alternative: Duplicating loading logic in train_model.py
Writing separate pd.read_csv calls in different files. Guarantees that preprocessing logic will drift over time.
⚖️

Why we used this specific approach over alternatives

Single DRY Ingestion Gateway: Centralizing data loading in load_data() ensures EDA and model training operate on the exact same cleaned data, preventing training-serving skew.
🧠

Memory Hook & Pattern to Remember (Cheat Sheet / Viva Tip)

DRY Ingestion: Have exactly one load_data() function in your project that validates, cleans, and is imported everywhere.

"""
Model Training & Explainability — Customer Churn Prediction

Class imbalance: churn is ~26.5% of the dataset. All three models are trained with
balanced class weighting (class_weight="balanced" for LR/RF, scale_pos_weight for
XGBoost) rather than left at the unweighted default:
  - Recall on the churn class goes from ~0.51 to ~0.79-0.80 across all three models.
  - Missing an actual churner is costlier than an unnecessary outreach.
  - Reported accuracy drops as an expected side effect — accuracy is a poor metric
    under class imbalance.

Model selection: the winner is chosen by mean 5-fold cross-validated ROC-AUC on
the TRAINING data, not by test-set score — so the held-out test metrics stay an
unbiased report instead of doubling as the selection criterion.
"""
🎯

Why is it used in this project?

Documents critical architectural decisions in code: explicitly prioritizing Recall over Accuracy because false negatives (lost customers) cost hundreds of dollars in lost lifetime value, whereas false positives (unnecessary retention calls/discounts) cost very little. Ensures models are selected via K-fold cross-validation on training data to prevent optimistic data leakage.
🔀

Was there any other way? (Alternative Approaches)

🔀 Alternative: Maximizing raw Accuracy
A naive model that predicts 'No Churn' for every customer achieves 73.5% accuracy while catching 0% of churners!
🔀 Alternative: Selecting best model on Test Set Score
Using test set to choose the winning model makes the test set part of training, biasing reported generalization performance.
🔀 Alternative: SMOTE (Synthetic Minority Over-sampling)
Tested and rejected: creates synthetic blended points. When performed before cross-validation, it creates massive data leakage (giving fake ~0.93 AUC). Balanced weighting achieves the same recall boost cleanly without data synthesis.
⚖️

Why we used this specific approach over alternatives

Principled MLOps Governance: Choosing models by cross-validation maintains test-set purity. Balancing weights directly in the loss function avoids synthetic sample distortion and keeps pipelines deterministic.

Accuracy Paradox: On imbalanced datasets, high accuracy is a trap. Optimize ROC-AUC and Recall with class weights (class_weight='balanced').

def prepare_features(df: pd.DataFrame):
    """Drop the ID column, encode Churn and every categorical feature.

    Returns (X, y, feature_names, encoders). `encoders` and the feature order are
    saved to disk so api/main.py can encode a live request identically to how
    training data was encoded — this is the coupling that makes /predict correct.
    """
    df = df.drop("customerID", axis=1).copy()
    df["Churn"] = df["Churn"].map({"Yes": 1, "No": 0})

    encoders = {}
    for col in df.select_dtypes(include=["object", "str"]).columns:
        le = LabelEncoder()
        df[col] = le.fit_transform(df[col])
        encoders[col] = le

    X = df.drop("Churn", axis=1)
    y = df["Churn"]
    return X, y, list(X.columns), encoders

def evaluate(name, model, X_test, y_test, results, roc_data, out_dir):
    """Score a fitted model, record its metrics, and save its confusion matrix."""
    preds = model.predict(X_test)
    probs = model.predict_proba(X_test)[:, 1]
    fpr, tpr, _ = roc_curve(y_test, probs)
    roc_data[name] = (fpr, tpr, roc_auc_score(y_test, probs))
    results.append({
        "Model": name,
        "Accuracy": round(accuracy_score(y_test, preds), 4),
        "Precision": round(precision_score(y_test, preds), 4),
        "Recall": round(recall_score(y_test, preds), 4),
        "F1": round(f1_score(y_test, preds), 4),
        "ROC_AUC": round(roc_auc_score(y_test, probs), 4),
    })
    cm = confusion_matrix(y_test, preds)
    plt.figure(figsize=(5, 4))
    sns.heatmap(cm, annot=True, fmt="d", cmap="Blues",
                xticklabels=["No Churn", "Churn"], yticklabels=["No Churn", "Churn"])
    plt.title(f"Confusion Matrix — {name}")
    plt.ylabel("Actual")
    plt.xlabel("Predicted")
    plt.savefig(os.path.join(out_dir, f"cm_{name.replace(' ', '_')}.png"), dpi=150, bbox_inches="tight")
    plt.close()

def train_models(X_train, y_train, X_test, y_test, X_train_scaled, X_test_scaled, out_dir):
    results, trained_models, roc_data = [], {}, {}

    # Logistic Regression: Scaled features + L2 tuning + balanced weights
    print("Tuning Logistic Regression...")
    lr_grid = GridSearchCV(
        LogisticRegression(max_iter=2000, class_weight="balanced"),
        param_grid={"C": [0.01, 0.1, 1, 10], "penalty": ["l2"]},
        cv=5, scoring="roc_auc", n_jobs=-1,
    )
    lr_grid.fit(X_train_scaled, y_train)
    evaluate("Logistic Regression", lr_grid.best_estimator_, X_test_scaled, y_test, results, roc_data, out_dir)
    trained_models["Logistic Regression"] = lr_grid.best_estimator_

    # Random Forest: Balanced weights + tree depth tuning
    print("Tuning Random Forest...")
    rf_grid = GridSearchCV(
        RandomForestClassifier(random_state=42, class_weight="balanced"),
        param_grid={"n_estimators": [100, 200], "max_depth": [5, 10, None], "min_samples_split": [2, 5]},
        cv=3, scoring="roc_auc", n_jobs=-1,
    )
    rf_grid.fit(X_train, y_train)
    evaluate("Random Forest", rf_grid.best_estimator_, X_test, y_test, results, roc_data, out_dir)
    trained_models["Random Forest"] = rf_grid.best_estimator_

    # XGBoost: Two-stage search (Structure first, then Regularization)
    pos_weight = (y_train == 0).sum() / (y_train == 1).sum()
    print("Tuning XGBoost (stage 1: model structure)...")
    xgb_grid = GridSearchCV(
        xgb.XGBClassifier(eval_metric="logloss", random_state=42, scale_pos_weight=pos_weight),
        param_grid={"n_estimators": [100, 200], "max_depth": [3, 5, 7], "learning_rate": [0.01, 0.1, 0.2]},
        cv=3, scoring="roc_auc", n_jobs=-1,
    )
    xgb_grid.fit(X_train, y_train)

    print("Tuning XGBoost (stage 2: regularization)...")
    xgb_reg_grid = GridSearchCV(
        xgb.XGBClassifier(eval_metric="logloss", random_state=42, scale_pos_weight=pos_weight, **xgb_grid.best_params_),
        param_grid={"reg_lambda": [0.5, 1, 2, 5], "reg_alpha": [0, 0.5, 1], "subsample": [0.8, 1.0], "colsample_bytree": [0.8, 1.0]},
        cv=3, scoring="roc_auc", n_jobs=-1,
    )
    xgb_reg_grid.fit(X_train, y_train)
    evaluate("XGBoost", xgb_reg_grid.best_estimator_, X_test, y_test, results, roc_data, out_dir)
    trained_models["XGBoost"] = xgb_reg_grid.best_estimator_
    return results, trained_models, roc_data

THRESHOLDS = np.round(np.arange(1, 200) * 0.005, 3)   # 0.005 .. 0.995

def calibrate_probs(p, class_weight_ratio):
    """Undo the odds inflation caused by class weighting.

    Training with class_weight="balanced" / scale_pos_weight=w multiplies the
    predicted odds of churn by w, so a raw 0.84 does NOT mean "84% chance".
    Dividing the odds by w puts the number back on the real-world scale.
    """
    p = np.asarray(p, dtype=float)
    return p / (p + class_weight_ratio * (1 - p))

def threshold_table(y_true, prob):
    """[threshold, tp, fp, tn, fn] for every threshold on the calibrated-probability
    scale — everything the dashboard needs to draw a confusion matrix and
    precision/recall at any cut-off."""
    y = np.asarray(y_true).astype(int)
    rows = []
    for t in THRESHOLDS:
        pred = prob >= t
        rows.append([float(t), int((pred & (y == 1)).sum()), int((pred & (y == 0)).sum()),
                     int((~pred & (y == 0)).sum()), int((~pred & (y == 1)).sum())])
    return rows
🎯

Why is it used in this project?

Solves a critical machine learning defect that most churn tutorials ignore: training with balanced class weights artificially shifts the prior odds, causing models to output inflated raw scores (mean 40% vs real 26.5%). calibrate_probs applies Bayes' rule inversion to restore genuine real-world probabilities. threshold_table precalculates confusion matrix counts across 199 thresholds to power the real-time threshold slider in the UI.
🔀

Was there any other way? (Alternative Approaches)

🔀 Alternative: Platt Scaling / CalibratedClassifierCV
Fits a secondary logistic regression on top of CV predictions. Requires extra fitting and often fails with extreme tree outputs.
🔀 Alternative: Leaving probabilities uncalibrated
Model outputs raw scores where 0.35 is called high risk. Confuses business stakeholders who expect probabilities to reflect empirical frequencies.
⚖️

Why we used this specific approach over alternatives

Exact Mathematical Closed-Form Prior Inversion: Because class weighting multiplies odds by $w = N_{neg} / N_{pos}$, dividing the predicted odds by $w$ recovers the true posterior probability: $p_{cal} = p / (p + w(1-p))$. It is exact for logistic loss and monotonic (preserving ROC-AUC).
🧠

Prior Shift Formula: When training with class weight ratio $w$, recover true probability with: p_cal = p / (p + w * (1 - p)).

        print(f"Missing packages: {', '.join(missing)}")
        print("Install them first:  pip install -r requirements.txt")
        sys.exit(1)

def _can_import(pkg):
    try:
        __import__(pkg)
        return True
    except ImportError:
        return False

def artifacts_exist():
    return all((OUTPUTS_DIR / f).exists() for f in REQUIRED_ARTIFACTS)

    except KeyboardInterrupt:

    finally:
        api_server.terminate()
        ui_server.terminate()
        api_server.wait()
        ui_server.wait()
